## Overview

Sanad (سند — Arabic for a legal instrument or deed) answers questions about **your own** legal
documents. It reads the PDFs and Word files you upload, indexes them at clause level, and answers
strictly from what they contain — with a source reference for every statement.

The design assumption is that in legal work an unverifiable answer is worthless. So Sanad inverts
the usual arrangement: **citations are constructed by the application, not generated by the model.**
The filename, page range and clause label attached to a source come from the parser and the chunker.
The model may only *reference* a marker Sanad supplied, and any marker it invents is stripped from
the answer before it is displayed.

If the retrieved passages do not settle a question, Sanad says so rather than filling the gap.

> **Sanad is an analysis tool, not counsel.** It does not give legal advice, and every citation
> should be checked against the source document before it is relied on.

## Features

| | |
|---|---|
| **Ask** | Grounded Q&A across one or many documents, with an inline `[S1]`-style citation on every factual sentence and a viewer for the exact passage behind it. |
| **Summary** | A structured brief of one document — purpose and parties, obligations, financial terms, term and termination, governing law, points needing a lawyer. |
| **Compare** | Two contracts, clause by clause: differing parties, clauses present in only one, changed obligations, dates, amounts and dispute-resolution terms. |
| **Key facts** | Schema-constrained extraction of contract type, parties, dates, obligations, payment terms, termination, renewal, penalties, governing law and deadlines. |
| **Bilingual** | Full Arabic and English interface with proper RTL layout. The answer language follows the *question*, independently of the interface. |
| **Scoped search** | Restrict retrieval to a subset of the loaded documents. |

**Supported formats:** PDF (`.pdf`) and Word (`.docx`).
PDFs carry page numbers into citations. DOCX has no pagination before rendering, so those citations
cite the clause and state that no page is available — Sanad never guesses a page number.

## RAG pipeline

```
upload → parse → chunk → embed → index ─┬─ dense (cosine)  ─┐
                                        └─ lexical (BM25)  ─┴─ RRF → MMR → cited answer
```

**1 · Parse.** PyMuPDF reads PDFs as layout blocks in reading order, so paragraph boundaries and
page attribution survive. python-docx walks the document body XML, which keeps tables in their true
position next to the clause that introduces them, and uses Word heading styles as structure.

**2 · Chunk.** A structure-aware packer targets ~1,200 characters and never splits a paragraph
unless it alone exceeds the ceiling. It starts a new chunk at each heading or numbered provision and
carries a sentence-aligned overlap so a clause spanning a boundary stays retrievable from either
side. Provision labels are recognised in both scripts — `Section 7.2`, `Article 12`, `المادة ٧`,
`البند ٣`, `§ 3` — and every chunk records its document, page range and section.

**3 · Embed.** Gemini embeddings via `:batchEmbedContents`, so a 100-chunk contract costs two
requests rather than a hundred. Documents are embedded with `RETRIEVAL_DOCUMENT` and queries with
`RETRIEVAL_QUERY`; vectors are re-normalised after dimensionality reduction so a dot product is a
true cosine similarity.

**4 · Retrieve.** Dense search finds paraphrases; BM25 over script-normalised tokens finds the
literal clause numbers, dates and amounts that embeddings blur. The two rankings are merged by
[reciprocal rank fusion](https://dl.acm.org/doi/10.1145/1571941.1572114), which needs no per-corpus
weight tuning, then reduced by maximal marginal relevance so six near-identical boilerplate clauses
do not crowd out the answer.

**5 · Answer.** The selected passages are rendered as a numbered, location-labelled context block.
The model is instructed to cite those markers and only those. Markers are verified against the
supplied set before rendering.

Nothing is written to disk. The index and the conversation live in the Streamlit session and are
discarded when it ends.

## Architecture

```
app.py                      Streamlit entry point — wiring only
src/sanad/
├── config.py               Frozen settings dataclasses; every default overridable by env var
├── i18n.py                 Both language catalogues and the translate() helper
├── errors.py               Typed errors, each carrying a translation key
├── documents/              Ingestion
│   ├── models.py           SourceDocument / TextBlock / Chunk / ParsedDocument
│   ├── loaders.py          PDF and DOCX parsing into structural blocks
│   ├── structure.py        Heading and provision-label detection (Arabic + English)
│   ├── chunking.py         Structure-aware chunk packer with overlap
│   └── library.py          The session's document collection and identity
├── llm/                    Model access
│   ├── transport.py        HTTP seam — the reason the suite runs offline
│   ├── gemini.py           REST client: batching, retries, redaction, parsing
│   └── prompts.py          Every prompt template, as plain functions
├── rag/                    Retrieval
│   ├── store.py            NumPy dense index + BM25 lexical index
│   ├── retriever.py        RRF fusion and MMR selection
│   ├── citations.py        Citation construction and marker verification
│   └── engine.py           answer() / summarize() / compare() / extract()
├── ui/                     Streamlit presentation only
│   ├── theme.py            Palette, typography, RTL layout
│   ├── state.py            Session-state accessors
│   ├── views.py            Sidebar, tabs, citation rendering
│   └── assets/             The Sanad mark (SVG)
└── utils/                  Text normalisation and language detection
tests/                      Offline test suite (no API key required)
```

Layers depend downward only: `ui` → `rag` → `llm`/`documents` → `utils`/`config`. The UI holds no
retrieval or prompting logic, and no module below `ui` imports Streamlit — so the entire pipeline
can be driven from a script or a notebook.

## Installation

Requires **Python 3.9 or newer** (verified on 3.9 and 3.11) and a Gemini API key.

```bash
git clone https://github.com/mohammedalmohawis/alsaree-legal-rag-assistant.git
cd alsaree-legal-rag-assistant
python3 -m venv .venv
source .venv/bin/activate
python -m pip install --upgrade pip
pip install -r requirements.txt
```

For development, install the package with its test and lint extras instead:

```bash
pip install -e ".[dev]"
```

## Configuration

```bash
cp .env.example .env
```

Open `.env` and set your key from [Google AI Studio](https://aistudio.google.com/apikey):

```bash
GOOGLE_API_KEY=your_gemini_api_key
```

### Environment variables

| Variable | Default | Purpose |
|---|---|---|
| `GOOGLE_API_KEY` | — | **Required.** `GEMINI_API_KEY` and `API_KEY` are also accepted. |
| `SANAD_CHAT_MODEL` | `gemini-3.6-flash` | Generation model. |
| `SANAD_EMBEDDING_MODEL` | `gemini-embedding-2` | Embedding model. |
| `SANAD_EMBEDDING_DIMENSIONS` | `1536` | Embedding width (128–3072). |
| `SANAD_TEMPERATURE` | `0.1` | Near-deterministic, so answers do not drift between runs. |
| `SANAD_CHUNK_TARGET_CHARS` | `1200` | Chunk size the packer aims for. |
| `SANAD_CHUNK_MAX_CHARS` | `1800` | Hard ceiling. |
| `SANAD_CHUNK_OVERLAP_CHARS` | `180` | Overlap carried between chunks. |
| `SANAD_TOP_K` | `6` | Passages sent to the model per answer. |
| `SANAD_CANDIDATE_POOL` | `24` | Candidates fused before MMR selection. |
| `SANAD_MMR_LAMBDA` | `0.72` | 1.0 = pure relevance, 0.0 = pure diversity. |
| `SANAD_DEFAULT_LANGUAGE` | `en` | Interface language at first load. |
| `SANAD_MAX_UPLOAD_MB` | `50` | Per-file upload ceiling. |

A malformed override falls back to its default rather than failing at startup.

On **Streamlit Community Cloud**, set `GOOGLE_API_KEY` in the app's Secrets rather than committing
a key. Secrets take precedence over environment variables.

## Running locally

```bash
streamlit run app.py
```

Then open <http://localhost:8501>, upload a PDF or DOCX in the sidebar, press **Process documents**,
and ask a question.

## Testing

```bash
pytest
```

214 tests, all offline — no API key and no network. The HTTP layer is a small injectable seam
(`sanad/llm/transport.py`), so the real client's batching, retry, redaction and parsing paths are
exercised against a scripted fake, and embeddings in tests are a deterministic bag-of-words vector
so retrieval assertions test genuine ranking rather than the shape of random numbers. PDF and DOCX
fixtures are generated at run time, so no binary files are committed.

Coverage spans document parsing, structure detection, chunk geometry and metadata, BM25, dense
search, rank fusion, MMR, metadata filtering, language detection, prompt construction, citation
construction and **verification of fabricated markers**, configuration resolution, error handling,
and the four engine features end to end.

```bash
ruff check .          # lint
pytest --cov=sanad    # coverage
```

## Limitations

- **No OCR.** A scanned PDF with no text layer is rejected with a message saying so, rather than
  indexed as an empty document.
- **DOCX citations have no page numbers.** Pagination does not exist until Word renders a file.
  Those citations name the clause and state that the page is unavailable.
- **Session-scoped only.** Nothing persists. Closing the tab discards the documents and the index;
  re-uploading re-embeds. This is a deliberate confidentiality choice, not an oversight.
- **Whole-document features are budgeted.** Summary, comparison and extraction read up to 60,000
  characters of a document (30,000 per side when comparing). Beyond that the result is flagged as
  covering the opening portion only.
- **Structure detection is heuristic.** Unusual numbering may not be recognised as a provision; the
  chunk still carries its page, so the citation stays valid, just less precise.
- **Retrieval is exhaustive, not approximate.** Excellent to a few thousand chunks; a corpus far
  larger than one office's active matters would want a dedicated vector database.
- **Some Streamlit widget chrome stays in English.** The file-uploader drop zone renders framework
  text that has no supported translation hook. Rewriting it with CSS `content:` tricks is
  deliberately avoided — that breaks silently whenever Streamlit changes its DOM.

## Security

- `.env` is git-ignored and must never be committed; `.env.example` holds placeholders only.
- The API key is read from Streamlit Secrets or the environment and is never hardcoded.
- The key travels in the `x-goog-api-key` **header**, never a query string, so it cannot leak into
  proxy or server access logs.
- Error messages are scrubbed of the key before they reach a screen or a log.
- Uploaded documents are held in memory for the session only — never written to disk, never sent
  anywhere but the Gemini API.
- Repository history has been scanned for exposed credentials; none are present.

Report a security concern via a private issue rather than a public pull request.
